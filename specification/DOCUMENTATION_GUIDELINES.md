# 项目文档编写规范

## 目标

让第一次接触项目的人能快速理解项目、找到正确的操作说明，并分辨当前实现、计划能力和历史方案。文档要解决读者的问题，避免重复堆叠相同信息。

## 每个项目必须有关键概念文档

每个项目都必须维护一份专门列出并解释本项目关键概念的文档，建议放在 `docs/核心概念.md`。如果项目已有稳定的文件命名惯例，可以使用带项目名的等效名称，例如 `docs/Node核心概念.md`。

该文档应：

- 列出理解项目所需的核心领域对象、角色、协议和容易混淆的术语；
- 对每个术语明确列出中文全称、中文简称、英文全称和英文简称；没有通用简称或对应名称时写 `—`，不要自行创造缩写；
- 给出简明定义，并说明概念在本项目中的具体含义和边界；
- 说明相近概念之间的区别，尤其是名称相似但职责、数据或安全属性不同的概念；
- 链接到负责流程、协议、接口、部署等细节的权威文档；
- 放入项目文档目录入口和 README 的相关文档链接中。

关键概念文档是术语的集中定义处，不是把全部设计、操作步骤或接口规范再抄一遍。可从 [KEY_CONCEPTS_TEMPLATE.md](./KEY_CONCEPTS_TEMPLATE.md) 开始编写。

## 文档职责和分层

按读者任务拆分文档，并为每份文档指定清晰职责：

| 文档类型 | 主要回答的问题 |
| --- | --- |
| README | 项目做什么，如何本地启动和验证 |
| 核心概念 | 项目中的关键对象、术语及其边界是什么 |
| 架构/设计 | 系统由什么组成，为什么这样设计 |
| 使用/操作指南 | 用户或开发者如何完成一项操作 |
| API/协议规范 | 请求、响应、状态、兼容性和错误语义是什么 |
| 部署/运维手册 | 如何发布、运行、观察、恢复和回滚 |
| 历史/决策记录 | 哪个决定在何时因何作出，当前是否仍有效 |

一份文档可以涵盖紧密相关的内容，但标题、开头和目录应让读者看得出它的职责。README 保持项目简介和本地快速开始；具体规则沿用 [README_TEMPLATE.md](./README_TEMPLATE.md)。

## 写作原则

1. **先给结论和适用范围。** 开篇说明文档面向谁、解决什么问题、哪些内容不在本篇范围内。
2. **围绕读者任务组织。** 说明概念、流程或步骤之间的因果关系，使用明确的小标题、表格和示例，不按修改历史堆叠内容。
3. **术语集中定义。** 关键概念在项目的概念文档中定义，同时记录中英文全称和简称。首次介绍时列明全称和简称；其他文档及后续正文可使用简称并链接回概念文档，不复制整套定义。
4. **细节只维护一份权威来源。** API 字段以 API/OpenAPI 规范为准，配置以实际模板或配置参考为准，操作步骤以对应手册为准。概览文档应链接权威来源。
5. **区分事实状态。** 明确标注已实现、规划中、实验性或已废弃的能力。计划内容不能写成当前行为；历史设计不能替代当前规范。
6. **以仓库事实为准。** 命令、路径、配置、接口、角色和示例须与当前代码及仓库文件一致。无法确认的内容应标明待确认，不能伪装为事实。
7. **写出边界和易混淆点。** 说明谁负责、谁持有数据/密钥、谁可验证或授权，以及相邻概念不能推出什么结论。
8. **示例可验证。** 示例值应可读且不含真实密钥、个人数据或生产凭证；命令和片段应验证可用，或标注为伪代码。
9. **控制篇幅。** 把面向不同任务的长内容拆到职责清晰的文档。需要跨文档阅读时使用相对链接，并提供阅读路径。

## 链接和维护

- 项目文档入口应列出核心概念文档，并按读者的推荐顺序组织其他文档。
- 使用仓库内相对链接；文件重命名、移动或删除时更新所有引用。
- 文档引用其他文档时要说明读者能在那里找到什么，避免只给一串没有上下文的链接。
- 术语定义、实现、接口或配置变化时，同一变更中更新对应权威文档和文档索引。
- 删除或替换文档前，检查是否仍有代码、线上页面、README 或其他文档引用它。
- 使用 Mermaid 等图表时，也要用文字说明关键边界；图表不能替代必要的定义和步骤。

## 发布前检查

- [ ] 项目有一份独立的关键概念文档，并已加入文档入口。
- [ ] 每个概念均列有中文全称、中文简称、英文全称和英文简称；不适用项已标明。
- [ ] 每份文档的读者、职责和权威范围清楚。
- [ ] 概念定义没有在多篇文档中互相矛盾或大段重复。
- [ ] 已实现、规划中、实验性和已废弃的内容区分明确。
- [ ] 命令、路径、字段和链接均已检查。
- [ ] 示例不包含真实凭证或不必要的个人信息。
- [ ] 文档结构能让读者从入口找到下一步所需内容。
